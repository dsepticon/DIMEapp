# Web-auth initialization contract and diagnostic review

Source baseline: `5e7a1f6`. Diagnostic pass: September 18, 2026. No fix deployment, authentication activation, real invitation, player-data access, secret-value retrieval, routing or privacy change is authorized in this pass.

## Confirmed cause and precision limit

The deployed handler initializes encryption, web identity, both Extension credentials and DynamoDB before inspecting the invitation payload. The prior synthetic probe (`A`-encoded malformed payload with an invalid signature) passed the old outer-shape gate, then received the outer initialization `503` from both the edge and direct API. It should have been rejected structurally without entering credential initialization.

Boolean-only Lambda metadata projections establish two additional configuration defects: **the resolved web identity and encryption entries are equal**, and **neither has the canonical shape of padded Base64 for a 32-byte key**. They are not ARN strings, unresolved dynamic references or JSON-object-prefixed values. The configured public client ID, origin, table, regions and mode flags match the reviewed targets. The template maps the two variables to the correct, distinct owner-supplied secret ARNs. Metadata confirms all three expected secrets exist and are not scheduled for deletion.

This proves a credential-bootstrap contract failure independent of the invitation: equal resolved keys cannot pass the old separation check, even if decoding succeeds. The old decoder also accepted noncanonical Base64 and lengths greater than 32, while the invitation verifier and AES-256 envelope require exactly 32 bytes. **It does not prove which old statement threw first.** The old catch discarded that information, and metadata-only checks cannot establish the actual encoding/decoded bytes. No secret values were fetched to remove this uncertainty. Do not label the stored value hexadecimal, a placeholder or an incorrect JSON field without evidence.

The corrected boundary is deterministic: malformed input returns 401 before keys; a structurally valid invitation encountering the observed noncanonical identity-key shape fails closed as `INVITATION_KEY_FORMAT`. Key-separation and encryption-format errors remain hard failures. The artifact fixes ordering and observability; it does not repair or replace the deployed secret material. Activation remains blocked pending a separately reviewed secure configuration correction and refresh. Do not silently rotate an identity/encryption key or infer that no persistent accounts exist from a failed request.

## One canonical secret representation

| Purpose                          | Secrets Manager representation                                                                                                                               | Lambda representation                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- |
| Twitch OAuth client secret       | Full plaintext `SecretString`: opaque nonempty ASCII provider secret; no JSON wrapper, quotes or whitespace                                                  | `DIME_OAUTH_CLIENT_SECRET`: resolved value, never ARN |
| Web identity/invitation HMAC key | Full plaintext `SecretString`: exactly 32 independently random bytes encoded as canonical padded RFC 4648 Base64, one line (44 characters including one `=`) | `DIME_WEB_ID_KEY_B64`: resolved value                 |
| Authentication encryption key    | Same encoding, independently generated and different from the identity and Extension keys                                                                    | `DIME_AUTH_ENCRYPTION_KEY_B64`: resolved value        |

No automatic trimming, hex decoding, base64url fallback, unpadded fallback or JSON-property guessing. Round-trip encoding must match. JSON objects such as `{ "WEB_IDENTITY_KEY": "..." }`, `{ "AUTH_ENCRYPTION_KEY": "..." }` or `{ "client_secret": "..." }` are documented **rejection fixtures**, not supported alternatives. Supporting a structured secret would require an explicit separately reviewed property selector in the CloudFormation reference; none exists now.

Current references select the entire `SecretString`, without a JSON key or explicit version. CloudFormation resolves them at deployment into the Lambda environment. The runtime does not expect an ARN and has **no Secrets Manager client**. Lambda's execution role has no GetSecretValue grant for the three expected ARNs or the unrelated synthetic ARN; simulation returns implicit deny. This is consistent with this architecture and is not evidence of a runtime secret-access failure. No IAM expansion is proposed.

All three secrets use AWS-managed `aws/secretsmanager` encryption and have no resource policy. No customer-managed Secrets Manager key requires a new runtime `kms:Decrypt` grant. The service that resolves deployment references still requires appropriate access. AWS explains [deployment-time resolution and refresh](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/dynamic-references-secretsmanager.html) and [customer-managed key permission requirements](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security-encryption.html). Updating only a secret does not automatically refresh a deployed Lambda value; any future correction must include a separately reviewed resource configuration refresh, keeping sign-in disabled until verification passes.

The runtime's lazy provider/repository adapters do not read or create a gameplay save while linking is disabled. Extension credentials are not decoded for rejected invitations. The original full four-key separation check remains before the first persistent authentication transaction and before link acceptance. Emergency logout/deletion continuation retains its independent web-key-only dependencies. Independent ARNs remain unchanged.

## Error confidentiality

Initialization errors expose only a generic 503 with a server-generated UUID correlation ID. The only new application log fields are `category` and `correlationId`; categories are runtime-allowlisted. Never log exceptions, causes, stacks, events, environment entries, secret ARNs, lengths, invitation text, provider data or request headers. Invalid client invitations produce no initialization log. Emergency logout retains expired cookies even on internal error. Callback initialization failure expires transient cookies; existing short TTL bounds abandoned login state.

SECRET_ACCESS is reserved for a failed secure preparation boundary. Synthetic access-denied/KMS-denied/timeout fixtures verify no writes on failed preparation; they do **not** imply that a runtime Secrets Manager client or live retrieval was tested. Adding such a client would need a different reviewed architecture and IAM permissions, outside this code-only change.
