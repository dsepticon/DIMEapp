## Original-universe bible (owner-approved Milestone 4.1 names)

**Premise and tone.** Destroya Industries operates a small but ambitious survey-and-recovery network in the invented **Cairncoil Reach**, within the **Lomrek** system. Players train as field operators, recover mineral samples, maintain vehicles, and support an expanding frontier. The tone is capable, practical and welcoming, with curiosity rather than militarism as the main driver. Destroya Industries is the principal employer; independent carrier and market organizations support the supply chain. Those groups are new setting proposals, not claims about the creator.

**Hierarchy.** **Tessick Station** is the orbital headquarters, with **Crew Ring** as the starting district. **Loam Crescent** and **Mica Slope** are distinct frontier mining worlds. **Avenbolt** is the large industrial city, and **Far Shards** is the remote claim region. These selected locations have explicit functional save mappings in the one-to-one matrix. They retain functions rather than geography, lore or visual forms of old places. Tessick uses radial service rings and pressure doors; Loam Crescent has wind-cut basalt terraces; Mica Slope has layered salt flats and flooded cuts; Avenbolt has stacked freight terraces, tram loops and vertical foundry streets. All geometry, signs, sprites and palettes require an independent art pass. Map silhouettes and layouts must be independently drawn, not recolored.

**Technology and economy.** Continuous-beam field tools are industrial devices. Hand and ground-rig extraction recover small deposits; ship rigs tackle larger lodes. Cargo may use new **load-unit** display nomenclature while retaining exact integer quantity semantics through migration. **Shift marks** is the selected currency display candidate; its balance remains numerically unchanged. Refining applies only to eligible ores. Market quotes and rewards remain server-defined. Existing price and rarity numbers must remain attached to their semantic legacy assets until each one-to-one replacement is reviewed; a proposed name does not authorize a value transfer.

**Naming and visual system.** Names favor industrial materials, terrain and utility, avoiding Star Citizen phonetics and manufacturer patterns. Graphics use original programmatic pixels: broad silhouettes, legible shape coding, muted slate/oxidized copper/teal proposals, and no borrowed logo geometry. Palette and branding are **original drafts**, not verified Dorathaadestroya brand colors. Interface terminology should use DIME-specific language, not copied game labels.

## Continuous-beam mining specification

All simulation quantities are integers, fixed 50 ms steps, with elapsed time clamped to prevent hidden-tab jumps. This is a proposed replacement for the current adjustable-power/explicit-fracture pass, not current production behavior. Server-issued immutable node parameters: rarity tier `r∈[0,4]`, size `s∈[1,5]`, mass `m∈[1,5]`, instability `i∈[0,100]`, mineral, yield units, seed and respawn epoch. Invalid parameters are rejected. Charge `q∈[0,1000]`.

| Parameter                     | Proposed integer formula                                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Charge gained per held tick   | `g = clamp(16 + 2r + 2s + m + floor(i/25), 16, 40)`                                                                                                                                          |
| Charge lost per released tick | `d = clamp(8 + floor(s/2) + floor(m/2) + floor(i/25), 8, 20)`                                                                                                                                |
| Optimal-band width            | `w = clamp(300 - 25r - 15s - floor(i/10), 120, 300)`; `lo=650-floor(w/2)`, `hi=lo+w`                                                                                                         |
| Stable ticks required         | `h = clamp(25 + 8r + 4s + 3m + ceil(i/10), 25, 100)` (1.25–5 seconds)                                                                                                                        |
| Deterministic disturbance     | `j = (hash(nodeSeed,tick) mod (2a+1))-a`, `a=min(4,ceil(i/25))`; only while held; clamp resulting charge. The bounded disturbance must be shown as a short trend cue.                        |
| Danger / destruction          | `q≥800` shows danger; `q≥1000` destroys node, yields zero pieces, marks it depleted and starts its normal server-defined respawn.                                                            |
| Stable progress               | Increase one tick only while `lo≤q≤hi`; otherwise decay by one tick per two elapsed ticks, bounded at zero. Laser need not stay held while charge coasts through the band, enabling pulsing. |

Tick order: apply held gain or released loss, add deterministic disturbance if held, clamp, check destruction, update stable progress, then resolve fracture when `progress≥h`. The beam exists only while held, in range, with clear line of sight, correct tool mode and focus. Releasing/focus loss/pausing stops the beam immediately; residual charge and HUD decay remain visible. A success automatically removes the intact node. A server-issued mining attempt records bounded start time and node/tool/generation; one resolution checks elapsed minimum/maximum, immutable node parameters, revision, range/zone eligibility, result limits and idempotent receipt. The server cannot attest real browser input; it does not trust client mineral, rarity, yield, price, piece list or reward. No per-frame database writes.

Piece count is `min(8, yieldUnits, 3 + floor((yieldUnits-1)/200) + floor((s-1)/2) + fragilityTier)` and node generation guarantees `yieldUnits≥3`. Piece amounts use `base=floor(yieldUnits/count)` plus one minor unit for the first `yieldUnits mod count` pieces in a seed-permuted stable order. Thus each is positive and the sum is exact. The historical 400-unit First Shift split (125/125/150) is preserved as a tutorial rule. For generated nodes, deterministic reachable-tile search ensures nonoverlap and smaller sprite radius than the intact node. If fewer than `count` valid tiles exist, generation rejects that node placement; it never drops yield. An exploded node has `collected=remaining=0`, `destroyed=originalYield` in the conservation ledger. Capacity rejection leaves the entire piece visible. No piece is removed until a unique server receipt accepts collection.

Extraction mode is explicitly selected with a mode button/key and does not fire on switching. Held vacuum input animates eligible pieces toward the player on the single canvas, with capped speed/particles. A bounded collection resolution is sent only when a piece reaches capture radius; server checks ownership, zone, node/piece state, tool range/line of sight, inventory capacity, revision/generation and receipt. Failed/timeout collection visually returns the piece to its authoritative ground tile. Refresh restores uncollected pieces; interrupted local charge restarts from zero unless a server-authorized attempt is still valid. Server state machine: `INTACT → ATTEMPT_ACTIVE → {FRACTURED, DESTROYED, INTACT}`; `FRACTURED → PARTIALLY_COLLECTED → DEPLETED → RESPAWN_READY → INTACT`. Destruction and depletion share a server-defined respawn policy. Define fixed budgets before implementation: one canvas; at most 8 pieces per node, 48 visible ground pieces, 24 active nodes per zone, 96 particles total, 24 per beam, 4 simultaneous beams. Test p95/worst frames and memory at Panel, Mobile and desktop; real Twitch/domain performance stays a later gate.

## Local-only prototype evidence and limits

`prototype.html` is served by Vite development mode only and is not a production HTML build input. `app/prototype/mining.ts` and `app/prototype/main.tsx` do not import the API client, canonical save factory, action schema, Twitch session or player identity. They use generic `Test Claim` and synthetic node parameters. The prototype has a local, explicitly named `sessionStorage` checkpoint for its own synthetic state so a refresh preserves remaining pieces and receipts. It writes only on node-phase, piece, capacity or fixture checkpoints, not on animation frames. A charging attempt restarts safely at zero charge after refresh. This is **not a DIME player save** and does not establish server anti-cheat, multiplayer ownership, authoritative persistence or respawn behavior.

The pure model has 11 focused tests: deterministic rise/decay/disturbance, rarity/size/mass/instability effects, pulsed stable hold, zero-yield explosion, exact splits for 3–8 pieces, non-overlap, positive units, full-capacity refusal, receipt replay and conflict rejection. The browser exercises Panel 318×500, Mobile 360×640 and desktop 1024×768, plus mouse, keyboard and simulated touch pointer input, reduced motion, refresh between fracture and extraction, synthetic network failure, capacity recovery, eight-piece stress and overcharge. [The prototype browser spec](../tests/e2e/m4Prototype.spec.ts) records screenshots under `/tmp/dime-m4-review/` (HUD and reduced-motion for each layout; fracture, full hold, vacuum, warning and destruction for Panel; eight-piece stress for each layout). The stress report is `/tmp/dime-m4-review/m4-performance.json`.

The 96-particle stress scene is a deliberately worst-case synthetic scene on one canvas, with eight actual pieces. On Linux x64, Chromium 153.0.8010.12 and 16 logical CPUs, 180 frames per layout measured rAF p95 of 16.7 ms (Panel/Mobile) and 16.8 ms (web), worst 16.8 ms. Instrumented canvas-render p95 was 0.2 ms in all layouts and worst 0.3 ms; DOM count stayed 62, canvas count 1, and there was no document scroll. These are Vite development-mode results, with no throttling or real Twitch webview. The rAF interval is a 60 Hz presentation cadence, not a GPU time measurement; separate canvas-render duration is reported in `/tmp/dime-m4-review/m4-performance.json`. This sample cannot establish production, Twitch webview or domain-browser performance. The browser cannot attest held input or line of sight, and this prototype does not connect to real server start/resolution actions. Those remain implementation and release gates.

## Shared web/Extension identity architecture

One game engine and API contract produce `twitch` and `web` builds. Web is an additional frontend on the eventual domain, not a replacement of the current website in this milestone. The backend resolves either verified Extension JWT `U` credential or verified web session to an internal random 128-bit-or-larger `accountId`; the account owns the one global save. Credential records hold namespace-qualified, HMAC-derived lookup keys, never assume Extension opaque `U` equals OIDC numeric `sub`. The client never supplies an account ID, partition key or starting save.

Web sign-in: server creates one-time state+nonce (and PKCE where supported), stores short-lived transaction server-side, sends browser to Twitch authorization-code/OIDC with only `openid`; callback verifies exact redirect, state, nonce, issuer/audience/expiry/signature, exchanges code using server-only secret, validates token, rotates session ID, sets `Secure; HttpOnly; SameSite=Lax` host-only cookie, and redirects to a clean path. No Twitch token in URL after callback, browser storage, bundle or logs. CSRF uses a server-bound synchronizer token on mutating cookie-authenticated requests plus Origin check; avoid broad CORS. Session TTL/idle timeout and rotation on login/link/privilege change; logout invalidates local session, revocation handling invalidates sessions, refresh is serialized and token ciphertext replaced atomically. Generic errors do not reveal account existence. Secret, redirect and infrastructure are separate later approvals.

Extension linking: authenticated persistent Extension session creates a one-use, five-minute intent bound to its existing derived credential, account/save generation and a random verifier; the web user independently signs in. The web page consumes the intent through a CSRF-protected POST after an explicit side-by-side account confirmation. A browser-open handle may transport only the one-use intent reference, never a Twitch credential/token; strip it from URL immediately, set `Referrer-Policy: no-referrer`, disable caching and logging of the handle. Transactionally compare both verified principals, intent TTL/unused state and generations, then attach credentials only if there is no conflict. Two populated saves, mismatched existing links, stale generations or simultaneous consumption stop with a generic conflict status for a separately designed resolution process, never auto-merge. Link receipt prevents replay. Unlink must preserve at least one verified login route and define ownership consequences; recovery uses verified identity, not entered opaque IDs. Privacy deletion is separate from gameplay reset and must cover account, both credentials, active sessions, gameplay and eligible receipts, with backup retention disclosed.

Threat-model gates: OAuth login CSRF/state swap, code replay, nonce mismatch, redirect abuse, cookie theft/CSRF, refresh-token rotation race, link-handle leakage/replay, cross-player linking, account collision, session fixation, unlink lockout, stale pending actions and reset-generation crossover. Synthetic cross-player, concurrent and replay tests precede any deployment. No user data, token or secret is needed for this design pass.

## Save migration and rollback proposal

The following proposal predates the owner's functional-equivalence decision. The approved mapping and current synthetic preview are recorded in the [one-to-one matrix](dime-m4-final-mapping.json) and [conversion tests](../tests/m4ContentConversion.test.ts). Statements below that say mappings still need owner approval are historical, not the current implementation gate.

Owner-approved initial link rule: if exactly one independently verified credential has established progress, that save becomes the account's save; if both have established progress, return a generic conflict status and preserve both unchanged. Do not create administrator read access or use player-data inspection as a shortcut. A later conflict-resolution process requires separate design approval. Introduce explicit `contentVersion` and `saveFormatVersion` before any conversion, with Milestone 3 dual-read compatibility and a previewable reversible transform. No permanent Star Citizen-to-original item mappings are approved. Numeric balance, ownership and historical labels remain bound to their original semantic records until each replacement is approved.

1. Inventory exact live schema and compiled source strings without reading real records. Build synthetic fixtures for every version, legacy quest, quantity version, work order, ship/equipment, node, location and receipt.
2. Add dual-read, old-write-compatible server code and account-ID shadow association only after owner review. Version every semantic mapping; do not reassign a source mineral/ship merely because a new label sounds similar. Carry stable legacy IDs and original display history until explicit approved mapping. New app versions must not open a save whose semantic version they cannot represent.
3. Require collision/conflict checks and transaction receipts for one-time account linking and any reviewed migration. Monotonic revision/generation guard prevents old pending actions from mutating converted saves. Keep original state in a versioned, recoverable format until a separately reviewed retention/rollback cutoff; no automatic merging.
4. Stage synthetic dry-runs and reversible dual-read deployment. Coordinate backend/web/Extension cutover only after compatibility matrix is green. Roll back binaries while old schema remains readable; if an irreversible write begins, rollback requires a reviewed inverse transform or a forward-fix, never silent restoration of another player's save.
5. No identity migration, save rewrite, OAuth registration or data access is performed in this pass.

Privacy draft (not a published policy): disclose internal random account ID, linked Extension and web credentials, server-held OAuth access/refresh tokens and validation, session cookies/CSRF, world/mining records, security/receipt retention, account unlinking, gameplay reset versus verified deletion, and backup window. Review actual operational retention and AWS region before writing final policy; no analytics, ads, purchases or Bits are added.
